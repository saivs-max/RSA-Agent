RSA Agent — User Guide & Automation Manual

Operations automation for RSA Weights & Measures (W&M) cart tracking. Ops managers talk to the agent in plain English from Slack; the agent updates the trackers, requests TRUNO inspections, parses field results, and hands carts off for W&M — and runs a set of background automations on its own.

Document covers two things: Part 1 is a first-time user guide for the people who talk to the agent. Part 2 is the reference manual for every scheduled task and trigger the agent runs today.

Part 1 — First-Time User Guide

1.1 What the RSA Agent does

The RSA Agent turns a plain-English request into a fully tracked workflow. You message it in Slack — “onboard these carts,” “what’s the status of cart 42,” or by dropping in an inspection form — and it does the bookkeeping across two Google Sheets, emails the TRUNO scheduler, posts the right reminders, and reads results back out of field paperwork. There is no rigid menu: the agent reasons about your message and calls the right actions in sequence.

Behind the scenes it connects four things: Slack (where you talk to it), a Python agent (the brain), a Google Apps Script web app (which writes to the sheets and sends email), and the RSA Tracker and TRUNO RSA Tracker Google Sheets. A web dashboard (Index.html) gives a read view of the same data.

1.2 Getting started

You don’t install anything. To use the agent you need: access to the Slack workspace where it lives, and the bot present in your channel. If it isn’t there yet, an admin invites it with /invite @RSA Agent in your W&M channel. You can also just direct-message the bot.

There are two ways to reach it:

Direct message (DM) — open a DM with RSA Agent and type normally. No need to tag it.

@mention in a channel — type @RSA Agent followed by your request in any channel it’s been added to. Use this when you want the rest of the team to see the exchange.

Say hi or what can you do? any time and the agent replies with its current capability list.

1.3 The cart lifecycle

Every cart moves through a predictable set of states. Knowing them makes the agent’s replies easy to read:

StageRSA StatusWhat it means
1. OnboardedPending Truno ScheduledCart is in the tracker and submitted to TRUNO. No inspection date yet — waiting on TRUNO to schedule.
2. TRUNO schedulesScheduled RSATRUNO confirmed a visit date. The agent writes that real date back, sets the ETS reminder, and posts a Coffee Break reminder.
3a. Inspection passesCompleted RSA → next step Pending W&MField form parsed as a pass. The CSM team is tagged to schedule the W&M test.
3b. Inspection failsFailed RSAField form parsed as a fail. Report link attached for follow-up.
4. W&M doneW&M status Passed W&MWeights & Measures inspection complete. Cart is finished.
(side) TRUNO cancelsresets to Pending RSAIf TRUNO cancels, the agent rolls the cart back and alerts the DRI.

A separate, informational Tech Result (calibration readings) is captured before the W&M test. It does not change the RSA or W&M status — the goal is simply that every cart ends up with both a Tech Result (calibration) and a Test Result (W&M pass/fail).

1.4 What you can ask the agent to do

Onboard new carts

Give the cart numbers, the store, and the state. Example:

onboard carts 1 and 2 at DEMO MART, Newark NJ

The agent will ask for the service trigger (Launches, Cart replacement, Load cell recal, W&M Failed, …) with clickable buttons — this is mandatory; nothing is added until you pick one. You can also state it inline to skip the prompt: … — trigger Cart replacement. On confirmation the agent generates the cart serials, adds rows to the RSA Tracker as Pending Truno Scheduled (with no invented date), creates the TRUNO request row, and emails TRUNO to schedule.

Check a cart’s status

status of cart 1 at DEMO MART  ·  what’s the status of P_WF_SHOPRITE_72_M3_001?

Returns a status card: RSA status, W&M status, overall status, DRI, and last-updated date.

Update status and add notes

cart 1 at DEMO MART — set W&M to Scheduled W&M, note: booked for Tue

The agent updates the field(s) and appends your note (existing notes are preserved), and stamps Last Updated to today.

Get filtered lists

show pending RSA carts in NJ  ·  stale carts  ·  carts for <DRI name>

See a summary dashboard

give me a summary — overall counts (pending / scheduled / completed RSA, pending / passed W&M, needs-action, stale) plus a breakdown by state.

Look up compliance requirements

what’s required for ShopRite, Newark NJ? — returns only the pre-launch and post-launch directives for that store/state, plus any flags (e.g. “Confirm Locally,” NY county exceptions). If the store isn’t in the guide by name, it falls back to a state-only match and says so.

Upload a W&M test (Scale Test) form

Drag a form (PDF/scan) into the bot DM with a note like “results attached.” The agent reads it, writes each cart’s Pass/Fail to the RSA Test Results column, attaches the report link, and sets Completed RSA (pass, tagging the CSM) or Failed RSA (fail).

Upload a tech calibration sheet

Upload the “Weight check checklist” spreadsheet. Any spreadsheet is automatically routed to Tech Results. For a photographed calibration sheet, add the word tech or calibration to your message so it isn’t mistaken for a W&M form. To force the destination, say rsa/test/w&m (W&M form) or tech/calibration (Tech Results) — the explicit keyword always wins.

Find gaps

which carts are missing tech results?  ·  carts missing test results  ·  what’s missing both?

1.5 The dashboard

The web app (Index.html) shows the tracker and archive in a browser, including the RSA Test Results and Tech Results columns (full text on hover, with links to the source files), a cart edit modal, and a CSV export. It’s a convenient read/spot-edit view of the same Google Sheet the agent writes to.

1.6 Guardrails — what the agent will and won’t do

These behaviors are deliberate and worth knowing:

It never invents a date. A cart stays Pending Truno Scheduled until TRUNO supplies a real visit date, which is then written back automatically. The service trigger is mandatory on onboarding — the agent will not add a cart without one. Notes are appended, never overwritten. Compliance answers return only pre/post-launch requirements, matched by store and address — never a raw data dump. When the agent can’t confidently match a record, it flags it for a human rather than guessing. And automated result-writing is idempotent — re-processing the same file writes nothing new.

Part 2 — Scheduled Tasks & Triggers Manual

This is the authoritative reference for every automated behavior the agent runs today. There are three independent layers, each with its own runtime and cadence:

A. Google Apps Script (GAS) time-based triggers — run on Google’s servers on a clock, as the script owner (so they can send Gmail). B. Python background monitors — start when rsa_agent.py launches and poll Drive folders on a short interval. C. Real-time Slack events — fire the instant a user messages or uploads. A fourth section documents the Truno status state machine the monitor acts on, and a fifth the request-driven web API actions.

2.1 Layer A — Google Apps Script time-based triggers

Installed by running createAutomationTriggers() once in the Apps Script editor; removed by removeAutomationTriggers(). The four managed triggers are:

Trigger functionCadencePurpose
masterDailyRunDaily at 9:00 AMUmbrella job — runs the alert/archive sweep and all three other automations in sequence.
monitorTrunoTrackerEvery 2 hoursSyncs the TRUNO sheet’s Status column back to the RSA Tracker (catches same-day scheduling).
ingestInspectionFilesEvery 4 hoursIngests Excel/CSV inspection files dropped in the Drive inspection folder.
emailNicoleForNewTrunoRowsEvery 15 minutesEmails the TRUNO scheduler for new agent-created visit rows (the agent itself can’t send mail).

masterDailyRun — daily at 9:00 AM

The umbrella job. It calls, in order and each wrapped so one failure doesn’t stop the rest: checkAndSendAlerts() (the existing alert/archive/progression sweep), then monitorTrunoTracker(), then checkCompletedVisits(), then ingestInspectionFiles(). Note that monitorTrunoTracker and ingestInspectionFiles also run on their own faster cadences (every 2h and 4h); the daily run is a guaranteed catch-all.

monitorTrunoTracker — every 2 hours (and inside the daily run)

Reads the TRUNO spreadsheet and acts on transitions in its Status column, writing changes back to the RSA Tracker. It is idempotent: each (row + status) is acted on at most once, keyed on trunoStore | icStore | cart | status in Script Properties (trunoProcessed). On its very first run it baselines all existing rows as already-handled (trunoBaselineV2) so it doesn’t re-fire emails/Slack for visits that were already scheduled or complete. The transitions it acts on are documented in Section 2.4.

ingestInspectionFiles — every 4 hours (and inside the daily run)

Scans the Drive inspection folder (INSPECTION_FOLDER_ID) for files it hasn’t seen. It processes only .xlsx, .xls, and .csv files; everything else is ignored. For each new file it parses the rows, adds/updates the matching rows in the RSA Tracker, writes a Tech Upload Link (col T) pointing at the source file, and archives a copy of the data as a timestamped sheet tab. Processed files are tracked by Drive file ID in Script Properties (ingestedFiles), so each file is ingested exactly once.

Note: this is the spreadsheet-based ingestion path. The vision-based Pass/Fail parsing of W&M Scale Test Forms is a separate, faster Python monitor (see Layer B) — don’t confuse the two.

checkCompletedVisits — runs daily inside masterDailyRun

This is not its own trigger; it executes once a day as part of masterDailyRun. It finds carts where RSA status = Completed RSA but W&M is not yet Passed/Completed, and where the last update was 3 or more days ago. For each such store it posts a “W&M Scheduling Needed” message to the CSM Slack channel and emails the CSM team. To avoid nagging, it re-alerts a given cart at most once every 3 days (tracked in Script Properties csmAlerts).

emailNicoleForNewTrunoRows — every 15 minutes

The Python agent writes TRUNO request rows directly via the Sheets API but runs as a service account and cannot send email. This trigger runs as the script owner (so GmailApp works) and emails the TRUNO scheduler for new agent-created rows. Its per-cart cadence is deliberate and self-limiting:

Keyed on store | cart (not the date, so it survives re-schedules), it sends exactly one initial request email when it first sees an agent-created row, then goes silent for 3 days (TRUNO_FOLLOWUP_DAYS). If after 3 days the row still shows no progress (no status change and no visit date), it sends exactly one follow-up nudge and then stops permanently. Any progress — a status change or a date appearing — stops emailing immediately. It skips rows that are completed/cancelled and any cart whose number contains “test.” On first run it baselines pre-existing rows so it never emails for visits that predate the trigger. State lives in Script Properties (trunoEmailed, trunoEmailBaseline).

Demo note: disable this trigger in Apps Script → Triggers before a demo so a test onboarding doesn’t email TRUNO; re-enable afterward.

2.2 Layer B — Python background monitors

Both monitors start automatically as daemon threads when rsa_agent.py launches; if a folder isn’t shared or set up, that monitor simply doesn’t start and Slack uploads still work. Both write monitor activity to the Slack channel set in RSA_MONITOR_CHANNEL.

MonitorCadence (default)WatchesWrites
drive_monitorEvery 300 s (5 min) — RSA_FOLDER_POLL_SECONDSW&M Scale Test Forms Drive folderRSA Test Results (col U) + report link (col T); sets Completed/Failed RSA
tech_monitorEvery 300 s (5 min) — RSA_TECH_POLL_SECONDSTech-results (calibration) Drive folder (TECH_RESULTS_FOLDER_ID)Tech Results (col V) + source link (col W). Does not change RSA/W&M status.
tech_monitor gap reportEvery 86,400 s (daily) — RSA_GAP_REPORT_SECONDS (set 0 to disable)—Posts a results-completeness report to RSA_MONITOR_CHANNEL

drive_monitor — W&M Scale Test Forms (every 5 min)

Polls the W&M test-form folder, vision-parses each new form (mixed scans/PDFs) into per-cart Pass/Fail, matches each result to a tracker cart by store number + cart number, and writes the result to col U (RSA Test Results) with the report link in col T. A Pass sets Completed RSA with next step Pending W&M and tags the CSM; a Fail sets Failed RSA. It only processes stores marked Forms sent = Yes in the TRUNO tracker, processes only new files, and is idempotent (re-running writes nothing). A self-trigger for testing is documented in 2.6.

tech_monitor — tech calibration readings (every 5 min) + daily gap report

Polls the calibration folder and parses the “Weight check checklist” spreadsheets directly (openpyxl — exact readings, no vision), handling .xlsx, .csv, native Google Sheets, and PDF/photo (vision fallback). It matches each row to a cart by store + cart number and writes a compact readings summary to col V (Tech Results) with the source link in col W. Writing a tech result is informational and does not change RSA/W&M status. It is self-healing (a sheet that lands before its cart exists is picked up on a later pass) and idempotent. Carts whose store+number aren’t in the tracker yet are reported as unmatched rather than dropped. Separately, on the RSA_GAP_REPORT_SECONDS cadence (daily by default) it posts a completeness report showing which carts are missing a Tech Result, a Test Result, or both.

2.4 The TRUNO status state machine (acted on by monitorTrunoTracker)

The live TRUNO sheet uses free-form status words, which are normalized to four canonical outcomes. Anything else (Pending Forms, Pending Customer, Duplicate, blank, …) is ignored.

TRUNO statusWhat the monitor does
PendingNo action — visit not yet confirmed by TRUNO.
ScheduledWrites RSA Vendor = TRUNO (col G), the confirmed visit date (col H), RSA Status = Scheduled RSA (col J), and an ETS Reminder date = visit date − 1 day (col I); stamps Last Updated (col R). Then posts an ETS Coffee Break reminder to the ETS Slack channel (put cart ON Coffee Break the day before, OFF on inspection day).
CompletedSkipped here — completion is owned by the Python drive_monitor, which reads the actual Scale Test Form so it can tell Pass from Fail and attach the report. GAS only marks the row processed so it doesn’t double-write.
CancelledResets the cart’s RSA status back to Pending RSA and alerts the DRI.
Ambiguous matchIf the monitor can’t confidently map a TRUNO row to a single cart, it flags it for a human instead of guessing. Unmatched rows aren’t marked processed, so they’re retried on later runs (e.g., once the cart is onboarded).
